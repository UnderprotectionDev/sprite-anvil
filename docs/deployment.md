# Deployment wiring

## Database migrations

The app reads `DATABASE_URL`. `bun run db:migrate` reads the same application target and uses `DATABASE_URL_UNPOOLED` when it names the matching direct Neon endpoint and database. When only a pooled Neon URL is available, the runner removes the endpoint's `-pooler` suffix for its direct connection. It rejects a mismatched direct URL, a direct URL supplied with a local target, non-Neon remote hosts, and a remote URL with `NEON_LOCAL=true`. `NODE_ENV` and `MIGRATION_DATABASE_URL` do not select a migration target. The migration guard applies only to database commands: a locally started app still connects to whatever `DATABASE_URL` names, including production when that URL points there. Inspect the runtime target separately before starting the app or worker locally.

For every remote migration, configure the direct Neon endpoint host assigned to the intended branch: `NEON_DEVELOPMENT_ENDPOINT_HOST` for development or `NEON_PRODUCTION_ENDPOINT_HOST` for deployment. Use only the hostname, such as `ep-example.us-east-2.aws.neon.tech`, with no credentials, scheme, or `-pooler` suffix. Define local values in ignored `packages/db/.env.local`; define deployment values in the deployment service's environment. The runner compares the selected URL's direct endpoint host with this trusted value before opening the database. Missing or mismatched settings stop the migration. A target label or deployment confirmation alone is insufficient. Keep each host setting tied to its intended Neon branch when endpoints change. CI receives `NEON_TEST_ENDPOINT_HOST` from the branch creation action's `db_host` output and uses `DB_MIGRATE_TARGET=test`. The migration runner itself needs no Neon Management API key or project ID. Host matching does not independently prove the current branch ID if a Neon endpoint is reassigned; that requires a fresh branch-to-endpoint lookup.

After changing `packages/db/src/schema/`, run `bun run db:generate` and review the new SQL and snapshot in `packages/db/src/migrations/`. Keep each schema change and its migration together. Do not generate a migration for a code change without a schema change. Do not edit an applied SQL file, directory name, or snapshot. The installed Drizzle Kit uses timestamped migration directories; adding `meta/_journal.json` would make its migrator reject the repository.

For development, inspect the database named by `DATABASE_URL`, then set `DB_MIGRATE_TARGET=development` and run `bun run db:migrate`. For loopback PostgreSQL, also set `NEON_LOCAL=true`. The runner refuses existing application tables without migration history, histories ahead of this branch, changed SQL hashes, gaps, changed order, and missing snapshot parents. It takes an advisory lock before the checks and holds it through application. If another workspace has applied migrations, integrate that Git history first. Recreate only a pending migration that has never been applied; preserve every applied migration and its metadata. A legacy database without history needs a separately reviewed, narrowly scoped reconciliation migration; this command has no bypass.

For a deployment, inspect the target database and run `DB_MIGRATE_TARGET=production DB_MIGRATE_DEPLOY_CONFIRM=production bun run --cwd packages/db db:migrate:deploy` in the deployment environment with `DATABASE_URL` and, if available, the matching `DATABASE_URL_UNPOOLED`. Apply it before starting the new app and worker release. This explicit command is separate from app startup and workspace scripts. The runner prints no URL or driver error details that may contain credentials.

`db:push` is only for a disposable local PostgreSQL database: set a loopback `DATABASE_URL`, `NEON_LOCAL=true`, and `DB_PUSH_DISPOSABLE=true` before running `bun run db:push`. Never use it to reconcile a shared or managed database. On pull requests, CI creates a temporary Neon test branch, applies migrations there, runs the database integration tests as blocking checks, and deletes the branch afterward. If either the CI repository variable `NEON_PROJECT_ID` or secret `NEON_API_KEY` is missing, the workflow writes an explicit skipped-check summary; set both to run the Neon-backed checks.

Railway infrastructure is defined in `.railway/railway.ts`. The app service builds the React site and Hono API together; Hono serves `apps/web/dist` and exposes `/health`. The worker service runs the Cloudflare Queues HTTP pull consumer. Both services use Railpack.

Connect both Railway services to this repository, then run `railway config plan` and review the proposed changes before applying them. This repository has no Git remote or linked Railway project, so service sources and domains cannot be inferred here.

Set `NODE_ENV=production`, `DATABASE_URL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, and `CORS_ORIGIN` on the app. Set `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_QUEUE_ID`, `CLOUDFLARE_QUEUES_TOKEN`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, and `R2_BUCKET` on both services. The worker also needs the existing server environment schema values because it imports that schema. Set `VITE_SERVER_URL` to the public app URL for the web build. R2 bucket CORS must permit `PUT` from that app origin with the `Content-Type` header. Enable HTTP pull on the Cloudflare queue and use a token with Queues read and write permissions.

Copy `cloudflare/r2-cors.example.json`, replace `https://example.com` with the exact web origin (scheme and host, no trailing slash), then apply it with `bunx wrangler r2 bucket cors set <BUCKET> --file <POLICY_FILE>`. Verify with `bunx wrangler r2 bucket cors list <BUCKET>`. The bucket and its live origin are account-specific, so this policy is a deployment template.

If the packaged desktop app will upload directly to R2, also configure and verify its platform origin (`tauri://localhost` on macOS or `http://tauri.localhost` on Windows/Linux) in the bucket policy. This cross-origin upload path needs a live bucket test on each packaged platform.

The queue transport currently checks that uploaded objects exist, then acknowledges the message. It does not yet implement the PRD's durable background operation record, transactional outbox, or reconciliation. Do not use this transport for consequential jobs until those records exist.

If deploying the separate Fumadocs site, set `NEXT_PUBLIC_DOCS_URL` to its public origin at build time. The local build uses `http://localhost:4000` for social metadata.
