# Deployment wiring

## Database migrations

The app reads `DATABASE_URL`. The guarded development launchers and migration runner authorize explicit targets before opening them. They use `DATABASE_URL_UNPOOLED` only when it names the matching direct Neon endpoint/database; otherwise a pooled Neon endpoint is converted to its direct host. They reject mismatched direct URLs, direct URLs on loopback, non-Neon remote hosts and remote URLs with `NEON_LOCAL=true`. `NODE_ENV` and `MIGRATION_DATABASE_URL` do not authorize an environment. Direct app/worker production startup remains separate and never auto-migrates. Inspect those runtime targets independently.

For every remote migration, independently configure the authorized direct hostname **and database name**: `NEON_DEVELOPMENT_ENDPOINT_HOST`/`NEON_DEVELOPMENT_DATABASE_NAME` for development or `NEON_PRODUCTION_ENDPOINT_HOST`/`NEON_PRODUCTION_DATABASE_NAME` for deployment. Use only a hostname without credentials, scheme or `-pooler`. Define local values in ignored `packages/db/.env.local` or secure Conductor repository settings, and production values in the deployment environment. A label, URL appearance or deployment confirmation alone is insufficient. Missing/mismatched declarations stop migration, and overlapping development/production identities are rejected. Reverify provider endpoint assignments when they change. No Neon Management API credentials are required.

After changing `packages/db/src/schema/`, run `bun run db:generate` and review the new SQL and snapshot in `packages/db/src/migrations/`. Keep each schema change and its migration together. Do not generate a migration for a code change without a schema change. Do not edit an applied SQL file, directory name, or snapshot. The installed Drizzle Kit uses timestamped migration directories; adding `meta/_journal.json` would make its migrator reject the repository.

The runner verifies the ordered applied prefix by migration name, timestamp, and SQL content hash. Migration record IDs must be positive, strictly increasing integers, but PostgreSQL sequence offsets or gaps do not indicate missing migration identities. An exact applied migration recovered from Git history must be integrated together with its original snapshot and schema before regenerating any pending migration; never change the database's recorded hashes to match different SQL.

For development, use `bun run db:prepare`, then `bun run db:ready`; `db:migrate` uses the same preparation path. Source validation requires local PostgreSQL binaries and does not contact shared targets. Targets are independently prepared under exclusive advisory leases; existing dev API shared leases block migration. Exact prefix history and actual schema are checked before and after canonical Drizzle Kit. Ahead/divergent history or drift stops application, not independent coding. Recover missing applied artifacts with their owning implementation/schema from trusted Git. Preserve applied and unknown-status migrations/metadata. No baseline or repair bypass exists. See [shared development database operations](development-database.md) for multiple targets, Run's read-only gate, historical inventory and agent delivery.

For deployment, configure the authorized production host/database and run `DB_MIGRATE_TARGET=production DB_MIGRATE_DEPLOY_CONFIRM=production bun run --cwd packages/db db:migrate:deploy` in a release environment with local `initdb`/`postgres` (or `DB_POSTGRES_BIN`), `DATABASE_URL` and optional matching `DATABASE_URL_UNPOOLED`. It validates source and verifies the production prefix/catalog under the same migration lease before/after canonical application. Coordinate a release window with production app/worker owners; production processes do not hold development leases. Apply before starting the new release. This command remains separate from Run/startup; Railway does not auto-provision PostgreSQL binaries or invoke it. Errors omit secret URLs/driver details.

`db:push` is only for disposable loopback PostgreSQL with `NEON_LOCAL=true` and `DB_PUSH_DISPOSABLE=true`; it never reconciles a shared/managed database. Pull-request CI installs local PostgreSQL binaries and runs disposable preparation/full-source integration tests without Neon branches, credentials or fake permanent history. The unused CI-Neon-branch test and alternative live migration test seam have been removed; provider drivers remain.

Railway infrastructure is defined in `.railway/railway.ts`. The app service builds the React site and Hono API together; Hono serves `apps/web/dist` and exposes `/health`. The worker service runs the Cloudflare Queues HTTP pull consumer. Both services use Railpack.

Connect both Railway services to this repository, then run `railway config plan` and review the proposed changes before applying them. This repository has no Git remote or linked Railway project, so service sources and domains cannot be inferred here.

Set `NODE_ENV=production`, `DATABASE_URL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, and `CORS_ORIGIN` on the app. Set `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_QUEUE_ID`, `CLOUDFLARE_QUEUES_TOKEN`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, and `R2_BUCKET` on both services. The worker also needs the existing server environment schema values because it imports that schema. Set `VITE_SERVER_URL` to the public app URL for the web build. R2 bucket CORS must permit `PUT` from that app origin with the `Content-Type` header. Enable HTTP pull on the Cloudflare queue and use a token with Queues read and write permissions.

Copy `cloudflare/r2-cors.example.json`, replace `https://example.com` with the exact web origin (scheme and host, no trailing slash), then apply it with `bunx wrangler r2 bucket cors set <BUCKET> --file <POLICY_FILE>`. Verify with `bunx wrangler r2 bucket cors list <BUCKET>`. The bucket and its live origin are account-specific, so this policy is a deployment template.

If the packaged desktop app will upload directly to R2, also configure and verify its platform origin (`tauri://localhost` on macOS or `http://tauri.localhost` on Windows/Linux) in the bucket policy. This cross-origin upload path needs a live bucket test on each packaged platform.

The queue transport currently checks that uploaded objects exist, then acknowledges the message. It does not yet implement the PRD's durable background operation record, transactional outbox, or reconciliation. Do not use this transport for consequential jobs until those records exist.

If deploying the separate Fumadocs site, set `NEXT_PUBLIC_DOCS_URL` to its public origin at build time. The local build uses `http://localhost:4000` for social metadata.
