# Separate historical approval from current applicability

Approval records the user's historical acceptance of an Asset Version and is never silently revoked by a later Context Revision or Canonical Design change. Review Disposition is derived from immutable Review Events, so rejection can later be followed by a new Candidate or Approved event without erasing the earlier decision; archival remains independent. A bulk approval first previews eligibility and blockers, then writes an individual Review Event for every approved item; it never silently skips, approves, or waives a blocked item. Lifecycle otherwise uses Applicability Status, QA Readiness, and Availability as separate dimensions. Derivatives carry typed Dependency Links for identity, silhouette, equipment, palette, theme, perspective, timing, and other relevant facets; a user-confirmed Change Facet marks matching direct and transitive dependencies Revalidation Required, while derivatives with incomplete dependency declarations are flagged conservatively. Revalidation Required blocks export against the current context until user re-review; a Quality Waiver cannot clear applicability, although a separate historical composition may pin the older context and dependency set. Replacing a Unit Version in one Composite Version is recorded as Composition Membership, not as a global “superseded” applicability state on the older unit, which may remain valid in other and historical compositions. This preserves truthful audit history and targeted current-export safety, at the cost of an event history, typed dependency graph, composition-scoped membership, and multiple status dimensions instead of one linear state.
