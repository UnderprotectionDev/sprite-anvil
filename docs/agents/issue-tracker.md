# Issue tracker

GitHub Issues in `UnderprotectionDev/sprite-anvil` is the tracker for published work. Resolve the repository from `git remote` before using `gh` in a different clone. Read and write issue state in GitHub; this repository does not define a Linear mirror.

## Selected issue in a Conductor workspace

At task start, inspect Conductor's selected issue context and any attachment named `.context/attachments/[GITHUB]-<number>.md`, where `<number>` is the issue number. Use the selected issue URL or canonical attachment to identify the issue in this repository; verify the repository against `git remote`. Read that GitHub issue, including comments and labels, with `gh issue view <number> --repo <owner/repository> --comments` before implementing it. A branch name, commit message, spec number, or unrelated issue mention does not establish which issue Conductor selected. If several attachments point to different issues, resolve which one is selected before treating any as the task. If Conductor supplied no selected issue and no canonical attachment identifies one, carry out the request as a general task without inventing an issue number.

## Schema migrations across parallel issues

For a selected issue that changes a table, column, or constraint, include the versioned migration in that issue's work. If a general task changes the schema, follow the same migration steps within that task. Do not generate a migration when the schema is unchanged or defer schema migrations until several issues or a spec are complete. Exception: an [`/implement-spec`](implement-spec.md#veritabanı) run generates each ticket's migration with that ticket and runs this workflow once on the integration branch.

1. Read [shared development database operations](../development-database.md) and inspect the schema, migrations, Drizzle config and package scripts. Verify the configured endpoint **and database name** are authorized development targets; a URL, branch name or `NODE_ENV` is not authorization. Workspaces use these shared targets; no workspace DB creation, deletion, baseline or promotion is part of issue development.
2. Run `bun run db:doctor` before generating or applying migrations. It reports pending migrations and other branches' migration records; those records are accepted by SQL hash and do not block generation, preparation or readiness. `bun run db:sync` is optional when this workspace needs another issue's code. Changed applied hashes remain blockers: restore the original SQL. Generate with `bun run db:generate` in the owning issue. Every new migration must be expansion-only (`bun run db:check`); a contracting change needs a first SQL line `-- parallel-safety: contract <reason>`. Review every generated SQL statement and snapshot against the intended schema change, including data loss, defaults and constraints. Keep code, schema, SQL and snapshot together. This installed Drizzle Kit uses timestamped directories, not `meta/_journal.json`. Code-only changes do not require a migration.
3. Run `bun run db:prepare` before DB-dependent validation. It validates source identities/snapshot lineage/schema and, under an exclusive lease, compares shared database introspection against reviewed pending SQL and pinned historical exceptions. Before writing pending development migrations, the command also requires a clean workspace whose complete HEAD is reachable from current origin/main or a verified origin PR, with matching committed SQL and snapshots. Commit the reviewed implementation, schema, SQL and snapshots together and publish the owning branch through a PR (a draft PR is sufficient) before preparation; main need not be merged first. Do this publication as part of the authorized issue delivery when allowed, otherwise report the precise publication blocker before shared DDL. It applies pending migrations by SQL hash in one transaction, verifies the result before commit and rolls back everything on failure. Development commands do not create temporary PostgreSQL; full replay is an optional explicit audit. `db:migrate` uses the same preparation path. If the only problem is pending migration(s), complete preparation yourself; do not hand this work to the user. Report independent per-DB outcomes after partial failure, not an all-or-nothing transaction.
4. When rebasing, move your unmerged migration to the end of main. Its directory name, order and date may change; the same SQL is recognized as applied. Never change or regenerate applied SQL, renumber applied files, edit migration records, manufacture a baseline or use `db:push` to conceal a conflict. Before removing or regenerating a pending migration, verify by SQL hash that it is absent from every permanent target; unknown status means preserve it and report uncertainty.
5. APIs using the shared database are stopped before migration. A held development API lease requires a coordinated migration window: ask the owning workspace to use `Stop`, then retry. Do not terminate another workspace. A DB connectivity/configuration/history blocker pauses DB-dependent execution, tests and **ready** delivery; continue independent code, unit tests and `bun run db:validate` while recording the blocker.
6. Run affected tests, prepare safe manual test data on the verified development target, and run `bun run db:ready` again immediately before delivery. Readiness alone does not create accounts or feature fixtures. Record the actual visible record/account, real route, exact English UI labels and expected outcome per the [close-out guide](implement-close-out.md). Report failed/skipped DB checks separately; do not label a blocked handoff ready. Run/dev checks runtime compatibility and never establishes delivery readiness.

## Read or update an issue

- For an issue number or URL, read its body, labels, and comments with `gh issue view <number> --comments`; fetch structured fields with `--json` when needed. A bare `#<number>` may refer to a pull request, so check `gh pr view` when the context is unclear.
- Search existing open and closed issues before creating one. [Draft issue files](../specs/) under `docs/specs/<phase>/issues/` are local source material; a `Status: ready-for-agent` line does not prove publication. Once a matching GitHub issue exists, use that issue for tracker state and avoid a duplicate.
- When publishing a draft, preserve its acceptance criteria and blockers, and link its owning `spec.md` and PRD requirement. Use `gh issue create --body-file <file>` for a multiline body. Apply the role from [triage labels](triage-labels.md) after checking the issue is specified enough for that role.
- Keep blockers visible. Prefer GitHub issue dependencies when available; otherwise record `Blocked by: #<number>` in the issue body and recheck the linked issue before claiming work.
- Use `gh issue comment`, `gh issue edit`, and `gh issue close` for authorized tracker changes. Reference GitHub issue numbers as `#<number>` in commits and pull requests.

## Pull requests and closure

A pull request is an implementation artifact, not a new issue intake path. If the pull request should close an issue on merge, put a supported reference such as `Closes #<number>` in the actual pull request body and target the default branch. Verify the body and closing link before reporting that closure is configured. A merged pull request without that reference may leave the issue open.

**Done when:** the issue read or write refers to the correct GitHub record, its spec and PRD context are traceable, any label or blocker matches the current GitHub state, and any schema change has a verified migration in the same issue or task.
