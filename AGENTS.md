# Sprite Anvil agent process

This is the always-loaded process for work in Sprite Anvil. Apply the full sequence to product behavior changes. For maintenance or documentation work, follow only the steps and references the change touches.

## Process

1. **Orient.** Before changing product behavior, name the owning term in [the repository glossary](docs/CONTEXT.md), the requirement ID and file in [the PRD](docs/prd/README.md), the owning [implementation spec](docs/specs/), the relevant [workflow phase](docs/workflow/), and every affected [ADR](docs/adr/). Record a path for each, or `none` after checking. The PRD defines behavior; the spec's `Testing Decisions` defines the test seam, while a glossary term or workflow phase alone does not establish delivery scope. Surface contradictions with exact paths before implementation.
2. **Name.** Use the glossary's canonical English technical names in code, contracts, and tests; use its paired Turkish product labels in Turkish product documentation. Interface copy is English and uses the English names. Its `_Avoid_` lists are binding.
3. **Stack.** Before changing implementation, inspect the relevant package configuration and read the nearest working code example. Reuse what the project already owns: build each responsibility with its [tech stack](docs/tech-stack.md) technology, `packages/` module, or existing shared code rather than a hand-rolled equivalent; a form uses TanStack Form, not per-input state. Installing a listed technology is pre-approved. A responsibility the stack does not cover, or a dependency or platform boundary it does not list, goes to the user before implementation; record the approved choice in the tech stack.
4. **Structure.** Before adding or moving application code, use [structure.md](structure.md) as the target ownership map and check the file's actual callers. Put feature-specific web components, forms, and views under `apps/web/src/features/<feature>/ui/`; put feature-specific server code under `apps/server/src/features/<feature>/server/`. Keep TanStack file route registrations in `apps/web/src/routes/`, app-wide code at the app root, and shared contracts, authentication, database, and UI primitives in their owning `packages/` directories. Compose an interface primitive missing from `@sprite-anvil/ui` under the owning feature's `ui/components/`. The tree shows possible locations, not delivered scope: create a feature directory only when it owns implemented code. Resolve stale or conflicting paths by actual ownership and report the deviation. Account for every moved file's imports, route links, tests, and configuration.
5. **Change.** Implement the owning PRD behavior within the affected ADR boundaries and the Structure ownership map. Use workflow phases for work breakdown and completion criteria, the owning spec's `Testing Decisions` for the test seam, and [acceptance scenarios](docs/prd/10-acceptance-scenarios.md) for applicable evidence. For changed behavior, write and run a focused failing test at that seam before implementation; cover affected failure paths, then run it again after the change. If the requirement does not settle a consequential product choice, resolve it with the user rather than inventing behavior.
6. **Close.** Recheck the Orient paths, chosen names, stack reuse, file ownership, test seam, generated files, and any in-file instructions. When adding or changing a spec section, update its `Testing Decisions` to cover that section. Run relevant checks and report delivered behavior, any new or contested stack choice, actual verification, and remaining limitations using [the close-out guide](docs/agents/implement-close-out.md). A review or commit is required only when the task calls for it.

## Conditional references

- **Domain documents:** Before changing `docs/CONTEXT.md` or an ADR, or when a needed term is missing, read [domain guidance](docs/agents/domain.md). Preserve the distinction between this repository's glossary and an in-product project's `context.md`.
- **Authentication and private project data:** Read the applicable requirements in [platform and operations](docs/prd/08-platform-and-operations.md) and the relevant privacy or permission [workflow phase](docs/workflow/). For Better Auth sessions, cookies, or account access, check the installed version's API and security guidance; test unauthorized, expired, and failed paths that the change affects.
- **Spec-wide implementation:** Before running `/implement-spec` or implementing several tickets of one spec in one workspace, read [implement-spec](docs/agents/implement-spec.md).
- **Issues:** At task start, check Conductor's selected issue context and any `.context/attachments/[GITHUB]-<number>.md` attachment. If an issue was selected, identify and read it before implementation using the [issue tracker guide](docs/agents/issue-tracker.md); read that guide before other tracker access too. Use [triage labels](docs/agents/triage-labels.md) when classifying or publishing an issue.
- **User-facing changes:** Follow [the close-out guide](docs/agents/implement-close-out.md) to give a usable manual check with real screens, controls, setup, and expected results. For a change without a visible flow, state that explicitly.

## Repository guardrails

- **Generated output:** Edit the source and regenerate. TanStack Router creates `apps/web/src/routeTree.gen.ts`; Varlock generates `src/env.ts` from each owning `.env.schema`. Better Auth schema generation is available through `bun run auth:generate`; inspect its output before accepting it.
- **Database delivery:** Follow the [parallel migration workflow](docs/agents/issue-tracker.md#schema-migrations-across-parallel-issues) for schema changes and DB-dependent delivery. Include reviewed versioned SQL and snapshots with the owning issue, publish the reviewed owning code/schema/SQL/snapshots to a trusted Git source before shared DDL as described in that workflow, run `bun run db:prepare` yourself for compatible pending history, and finish with `bun run db:ready`. A DB blocker pauses DB-dependent execution and ready delivery, not independent implementation. Keep new migrations expansion-only (`bun run db:check`); other branches' migration records are accepted by SQL hash, and applied SQL is never changed or regenerated. Preserve applied artifacts and records. Run/dev is read-only and never prepares a DB. Reserve `db:push` for explicitly disposable loopback databases.
- **Branches:** Write Git branch names in English.
- **Code quality:** Use [package scripts](package.json) and [Biome configuration](biome.json) for Ultracite formatting and checks. Keep controls semantic and keyboard accessible, validate external input at its boundary, use descriptive errors, and make new modules focused with direct imports rather than catch-all barrel exports.
